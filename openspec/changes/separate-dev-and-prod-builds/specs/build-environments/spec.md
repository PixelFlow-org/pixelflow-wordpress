## Purpose

Defines how one build produces a production and a development archive of the plugin, where
each takes the PixelFlow service addresses it talks to, and how the server side and the admin
app of an installed plugin read them, so a development build never reaches production
services and the production build stays as it is.

## ADDED Requirements

### Requirement: One build produces both archives

The build script SHALL take no argument and SHALL produce, in one run,
`build/pixelflow.zip` from the production env file and `build/pixelflow_dev.zip` from the
development env file. Each archive's admin bundle and configuration SHALL be built from that
archive's env file. The archives SHALL contain the same plugin files and SHALL differ only in
the admin bundle and the configuration. Both SHALL unpack to a `pixelflow` directory.

#### Scenario: Both env files are present

- **WHEN** the build runs with `app/source/.env` and `app/source/.env.dev` present and complete
- **THEN** it produces `build/pixelflow.zip` and `build/pixelflow_dev.zip`, and replaces any
  archive left by an earlier build

#### Scenario: The archives differ only in their bundle and configuration

- **WHEN** both archives are unpacked and compared
- **THEN** every file except the admin bundle and the configuration file is identical

#### Scenario: The build is given an argument

- **WHEN** the build runs with any argument, including the former `dev` or `prod`
- **THEN** it exits non-zero with a usage message and builds no archive

### Requirement: Env files and their keys

The production addresses SHALL be read from `app/source/.env`, which is committed. The
development addresses SHALL be read from `app/source/.env.dev`, which the repository's own
ignore rules keep out of version control. Each env file SHALL define three keys, all
non-empty: `VITE_API_BASE_URL` (the API origin), `VITE_UI_BASE_URL` (the dashboard origin) and
`VITE_CDN_URL` (the address of the tracking script).

#### Scenario: The production env file is missing

- **WHEN** the build runs without `app/source/.env`
- **THEN** it exits non-zero naming the missing file and builds no archive

#### Scenario: A key is missing or empty

- **WHEN** an env file that exists lacks one of the three keys or sets it to an empty value
- **THEN** the build exits non-zero naming the file and the key, and builds no archive

#### Scenario: The development env file is missing

- **WHEN** the build runs without `app/source/.env.dev`
- **THEN** it produces `build/pixelflow.zip`, warns that the development archive was skipped,
  and leaves no `build/pixelflow_dev.zip` from an earlier build

#### Scenario: The development env file stays out of version control

- **WHEN** `app/source/.env.dev` exists in a clone of the repository
- **THEN** version control lists it as ignored, on any machine, without relying on a user's
  global ignore rules

### Requirement: Each archive carries the configuration of its environment

Each archive SHALL carry a configuration file holding the three addresses of its environment,
generated by the build from that environment's env file. The configuration file SHALL NOT be
committed.

#### Scenario: Production archive

- **WHEN** `build/pixelflow.zip` is unpacked
- **THEN** its configuration holds the three addresses from `app/source/.env`

#### Scenario: Development archive

- **WHEN** `build/pixelflow_dev.zip` is unpacked
- **THEN** its configuration holds the three addresses from `app/source/.env.dev`

#### Scenario: The generated configuration is not committed

- **WHEN** a build has written configuration files
- **THEN** version control reports none of them as new or modified

### Requirement: The working tree gets the development configuration

The build SHALL also write a configuration file into the working tree, so that the plugin
running from sources has addresses: from `app/source/.env.dev` when it exists, and otherwise
from `app/source/.env` with a warning that the working tree now talks to production.

#### Scenario: Development env file present

- **WHEN** the build runs with `app/source/.env.dev` present
- **THEN** the plugin running from the working tree uses the development addresses

#### Scenario: Development env file absent

- **WHEN** the build runs without `app/source/.env.dev`
- **THEN** the plugin running from the working tree uses the production addresses, and the
  build output says so

### Requirement: Server-side sends and the tracking script use the configured addresses

Every request the plugin's PHP side makes to PixelFlow, and the tracking script it adds to
storefront pages, SHALL use the addresses of the installed configuration. No PixelFlow service
address SHALL be fixed in the PHP sources.

#### Scenario: Storefront tracking script

- **WHEN** a storefront page loads with the plugin configured and tracking on
- **THEN** the page loads the tracking script from the configured script address, and the
  script is told to send to the configured API origin followed by `/event`

#### Scenario: WooCommerce and form events

- **WHEN** a WooCommerce event or a form event is sent, or a blocked event is reported
- **THEN** the request goes to the configured API origin followed by `/event` or
  `/blocked-events`

#### Scenario: Production addresses are unchanged

- **WHEN** a site runs `build/pixelflow.zip` built from the committed `app/source/.env`
- **THEN** its tracking script, events and blocked-event reports use the same addresses as
  before this change

#### Scenario: Development archive stays off production

- **WHEN** a site runs `build/pixelflow_dev.zip`
- **THEN** no request from the plugin's PHP side and no tracking script it adds uses a
  production address, unless the development env file itself names one

### Requirement: The admin app uses the configured addresses

The settings page SHALL take the API, dashboard and script addresses from the installed
configuration, passed to the page by the plugin. Any address a library fixes when the bundle is
built SHALL come from the same env file as the archive's configuration.

#### Scenario: Requests from the settings page

- **WHEN** the settings page signs in or calls the PixelFlow API
- **THEN** the requests go to the configured API origin

#### Scenario: Dashboard links

- **WHEN** a person follows any "open the dashboard" link or button on the settings page
- **THEN** it opens the configured dashboard origin followed by `/dashboard/overview`

#### Scenario: Sign-in window

- **WHEN** a person signs in or signs up from the settings page of either archive
- **THEN** the sign-in window opens on that archive's dashboard origin, never the other
  environment's

#### Scenario: Script parameters saved on connect

- **WHEN** the settings page saves the tracking script parameters after a site is connected
- **THEN** the saved API endpoint is the configured API origin followed by `/event` and the
  saved script address is the configured script address

### Requirement: Without configuration the plugin sends nothing

A plugin with no configuration file SHALL add no tracking script and SHALL send no event and
no blocked-event report, and SHALL load without PHP errors.

#### Scenario: A clone that was never built

- **WHEN** the plugin runs from a working tree that has no configuration file
- **THEN** storefront pages carry no tracking script, no request reaches `/event` or
  `/blocked-events`, and no PHP error or warning is raised
